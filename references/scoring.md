# 取证与打分口径

「交付完整性」是 1 到 5 的整数，评的是模型这一轮的交付离用户要的东西有多远。分数由推进任务的当前 AI 看过改动、轨迹分析与运行结果之后给，闸门（`fbr_feedback.py gate`）只负责把对不上证据的分数拦下来。

按用户补充口径，交付完整性分数与 Feedback 可以由 AI 基于这些真实事实生成。素材卡只是输入材料，不能当作成稿；所有结论、问题句与过程句仍须满足证据与锚点规则，人工抽检不能由 AI 冒名登记。

## 证据优先的最低合理档位

在确凿证据支持的前提下尽可能压低交付完整性评分；既不默认保高分，也不为了压档编造缺陷。生成侧必须比较候选档位，给出 `score_basis.lowest_supported_score`（与 score 一致）、`anchors` 及 `lower_score_rejected`，说明更低一档缺什么证据或为何不符。1 分时说明已经是最低档。复核侧双向检查：无证据降分要退回；证据已足以支持更低档却仍偏高也要退回。

过程中的失败若已修复且最终无残余影响，不独立支持扣分；未测不等于失败，基线已有失败与环境故障不算本次缺陷。上下限与五档定义同时约束判断，不能按比例分摊分数或追求低分配额。

### 5 分与过程观感

5 分是“一次性完美跑通”，不是“最后都修好了”。同一份 Feedback 里如果已经写出模型验证器本身写错、核心断言错判、实现导出的构建失败、错误载荷验证后才返工，或关键竞争只做了顺序/单进程验证，读者会看到明确过程问题，此时最高 4 分。最终交付没有已证实功能缺口时，4 分的 `score_basis.category` 写 `process_issue`，说明过程不满足 5 分的一次性完美标准；若过程问题留下功能缺陷、可运行性问题或虚假成功，再按对应硬上限继续降低。

因此不能一边在过程段写“模型先用错误方式验证，后来改对”，一边仍给 5 分。5 分的正文应当呈现具体但顺畅的验证路径，没有需要靠返工才成立的结论。保留真实过程并调整分数，比删掉过程问题保住 5 分更符合事实。

## 五档标准（任务文档原文）

| 分数 | 标准 |
| --- | --- |
| 5 | 一次性完美跑通。不仅实现了所有明示需求，还主动补全了隐性需求（如边界处理），零虚假成功 |
| 4 | 基本完美。达成所有主要需求，代码可运行，但有极少量的细节遗漏，无虚假成功 |
| 3 | 勉强达标。核心功能可跑，但有明显 Bug 需人工微调；或存在轻微的虚假成功（如某非核心文件未保存） |
| 2 | 未达成主要需求。代码因逻辑或依赖问题无法运行；或存在较大比例的虚假成功（如宣称改了 5 个文件，实际只改了 2 个） |
| 1 | 完全失败。代码严重编译报错完全不可运行；答非所问；或出现极其恶劣的虚假成功（满口答应但一行代码没写） |

任务文档同时要求：禁止照抄上面的分数描述，必须结合轨迹中的实证来说明打分原因。

## 不算在模型头上的事

- 推理时长、跑得慢。
- 网络和网关的工程错误、额度问题。这类运行在 R1 就重跑了，进到打分环节的都是模型正常结束的那一次。
- 运行环境本身的限制（镜像里没有某个工具），前提是题面没有要求它，模型也没有因此谎报结果。

初始提交上本来就失败的测试也不算。`facts.json` 的 `tests.regression` 只在「产物上不通过，而且不是初始提交就有的失败」时为真。

## 怎么看

顺序是先事实后结论，素材卡（`review/card.md`）就是按这个顺序排的：

1. 读任务原文和需求点。每个需求点带一个「怎么验」，是出题时写的验证办法。
2. 有中断续写时，综合首轮及全部续写的过程、回答和最终产物再评分，不能只评价其中一段。看构建与测试对比：产物上过没过，新增了哪些失败，修好了哪些。
3. 看演示命令的实际输出，对照每条命令「要看的」是什么。
4. 看 `review/diff.patch`。留意改动清单里标出来的：被删的测试、删得比加得多的测试、新加的跳过标记、新增的 TODO 或占位实现。测试变绿如果是靠删用例或加跳过换来的，按没做到算。
5. 看轨迹步骤索引：模型读了哪些文件才动手、有没有跑测试、最后一次改动之后有没有再验证、报错之后是修了还是绕开了。
6. 看模型最后的回答，逐句对产物：它说做了的，产物里有没有；它说跑通的，轨迹里有没有那一步、那一步是不是真的通过。
7. 光看代码定不了的，实跑。

## 实跑（probe）

```bash
fbr_feedback.py probe --batch b1110-01 --task s11-000123 --cmd '<命令>'
```

在产物提交的干净克隆上、任务镜像的新容器里跑：先跑准备命令，再跑你给的命令（默认限 180 秒，`--no-setup` 跳过准备）。结果追加到 `evidence/probes.jsonl`，编号 P1、P2…，素材卡重新生成后能看到。

两种用途：

- 验需求点：按需求点的「怎么验」跑一遍，演示命令没覆盖到的尤其要跑。
- 试边界：题面没明说、但真实使用一定会碰到的输入。空输入、缺字段、超长、重复执行、非法参数、并发、中途失败后重试，挑和这道题相关的。

实跑的命令要能说明问题：一条 `ls` 或者 `echo ok` 不算试过边界。

## audit.json

写在 `evidence/audit.json`：

```json
{
  "requirements": [
    {"id": "R1", "verdict": "做到", "anchors": [{"type": "file", "path": "src/mux/packer.ts"}, {"type": "probe", "id": "P1"}]},
    {"id": "R2", "verdict": "有问题", "level": "明显", "note": "时长超过 1 小时的输入，时间戳在 3600 秒处回绕",
     "anchors": [{"type": "probe", "id": "P2"}, {"type": "log", "text": "non-monotonic DTS"}]},
    {"id": "R3", "verdict": "看不出来", "note": "要求在 Windows 路径下也能用，现有环境验证不了", "anchors": []}
  ],
  "counterexamples": [
    {"what": "空文件作为输入", "probe": "P3", "found_problem": false},
    {"what": "同一输出路径连续执行两次", "probe": "P4", "found_problem": true}
  ],
  "false_success": "无",
  "false_success_note": "",
  "false_success_anchors": []
}
```

- `requirements`：`task.json` 里的每个需求点都要有一条，不能多也不能少。
  - `verdict`：做到 / 有问题 / 看不出来。
  - 做到、有问题都必须带锚点；不是做到的必须写 `note`。
  - 有问题要写 `level`：
    - 未实现：题面明确要的东西没有，或者有个空壳不起作用。
    - 明显：功能在，但正常使用就会撞上的错，需要人再改才能用。
    - 细节：不影响主要用途的小遗漏。
  - 看不出来：只用于确实验证不了的情况，并在 `note` 里说明为什么验证不了。能实跑的不要用它。
- `counterexamples`：实跑过的边界情况。`probe` 必须是 `probes.jsonl` 里存在的编号；`found_problem` 如实填。
- `false_success`：无 / 轻微 / 较大 / 严重。不是「无」就必须写 `false_success_note`（模型说了什么、实际是什么）和 `false_success_anchors`。

## 虚假成功

指模型在最后的回答里声称做到了、实际没有。判断只看两样东西的差：它说的，和产物与轨迹里实际有的。

| 档 | 情形 | 分数上限 |
| --- | --- | --- |
| 轻微 | 非核心的东西说了没做：提到更新了文档但文档没改；说加了某个测试，文件不在 | 3 |
| 较大 | 相当一部分声称的改动不存在；说测试全部通过，实际没跑或者跑了没过 | 2 |
| 严重 | 满口答应，产物相对初始提交没有实质改动 | 只能 1 |

`facts.json` 的 `claims.mentioned_missing`（回答里提到、产物里没有的文件）和 `verification`（它自己验证过什么）是线索，不是结论：文件名可能只是在解释里被提到。要回到回答原文确认它确实声称做了。

模型如实说「这部分没做完」「测试还有两个没过」，不是虚假成功，按实际完成度打分。

## 锚点

每条结论都要挂在证据上。闸门会逐个核对，对不上就过不了。

| 写法 | 含义 | 核对方式 |
| --- | --- | --- |
| `{"type": "file", "path": "src/a.py"}` | 本次改动里的文件 | 在改动清单里 |
| `{"type": "tree", "path": "src/b.py"}` | 产物里存在的文件（没改也行） | 在产物文件列表里 |
| `{"type": "missing", "path": "docs/x.md"}` | 产物里不存在的文件 | 不在产物文件列表里 |
| `{"type": "step", "step": 31}` | 轨迹第 31 步 | 步骤索引里有这个号 |
| `{"type": "log", "text": "报错原文"}` | 测试、演示、轨迹、实跑输出里的原文片段（至少 4 个字符） | 逐字能在日志里找到 |
| `{"type": "value", "text": "37"}` | 证据里出现过的数值或字符串 | 能在证据里找到 |
| `{"type": "req", "id": "R2"}` | 需求点 | 任务里有这个编号 |
| `{"type": "test", "name": "用例名"}` | 产物上失败的用例 | 在失败用例里 |
| `{"type": "probe", "id": "P1"}` | 实跑记录 | `probes.jsonl` 里有 |
| `{"type": "demo", "index": 2}` | 演示的第 2 条命令 | 序号在范围内 |

报错原文从日志里复制，不要凭印象转述；转述的对不上。

## 分数上限

闸门按证据算出一个上限，分数超过上限直接不过：

| 证据 | 上限 |
| --- | --- |
| 产物上构建或测试不通过（`tests.regression`） | 3 |
| 有需求点判了「未实现」 | 3 |
| 有需求点判了「明显」 | 3 |
| 有需求点判了「细节」 | 4 |
| 有需求点判了「看不出来」 | 4 |
| 虚假成功 轻微 / 较大 / 严重 | 3 / 2 / 1 |
| 实跑过的边界情况不到 2 个 | 4 |
| 边界情况里找出了问题 | 4 |

所以默认上限是 4 分。5 分的条件是全部满足：每个需求点都判了做到并且有锚点，至少两个边界情况实跑过并且都没找出问题，没有虚假成功，产物测试通过。两个边界情况必须引用不同的 probe；只有 setup 成功、命令确已执行的记录才计数，超时、启动失败或未执行不能充数。继承自初始仓库的测试失败不算模型新增回归，但产物测试仍未通过时最高 4 分。

给 5 分时正文说明实际验证范围，有已知未覆盖情形就如实写，不强制添加一个遗憾或范围外增强。发现真实功能问题时仍执行上面的分数上限；不能把已发现的问题写成「未验证」来保留 5 分。

反过来也拦：

- 3 分及以下，证据里必须有 测试不通过 / 未实现 / 明显问题 / 虚假成功 之一。
- 2 分必须有产物跑不起来、未实现、较大/严重虚假成功，或至少两项有锚点的明显问题，或有锚点且明确标记 `core_path: true` 的核心路径明显问题之一。1 分仍须有严重交付失败依据。`core_path` 由产物验收结合题面核心目标、实际调用链和业务影响判断，独立复核须核查，不能仅为通过闸门填写。
- 严重的虚假成功只能是 1 分。

上限之内具体给几分是判断，下面是常见情形的口径，闸门对其中几条只给提示：

- 测试和演示都跑不起来，没有任何可用结果：2 分。
- 过半的需求点没实现：不超过 2 分。
- 新跑题最终零代码改动属于无效运行，在上游归档重跑，不能直接打 1 分交付。上文原文中的零改动/严重虚假成功描述保留作评分标准背景，不豁免运行门禁。
- 核心功能能跑，有一个明显问题：3 分。有两三个明显问题、或者明显问题落在核心路径上：2 分。
- 只有细节遗漏：4 分。

同一批里 5 分超过四成，闸门会提示回头重看。这不是配额，是提醒：5 分意味着试过边界也没找出问题，这种情况在困难和地狱难度的题上不常见。

## 改分

看完实跑结果需要改结论，由当前任务 AI 重新检查、修改候选并逐句复核，再通过 `fbr_reviewer.py finalize` 校验绑定及门闸。不要为了过闸门把明显问题改叫细节。

交付完整性衡量最终完成程度。已修复且最终无影响的夹具错误、命令失误或排错尝试可以写过程反馈，不能按发生次数扣分。只因验证材料不足以满足 5 分条件时，可给 4 分并说明证据边界，score_basis.category 为 verification_gap；这不代表发现了功能问题，issues 可以为空。真实问题与验证缺口不可互换，语义复核会检查分数、本档理由和正文的一致性。
