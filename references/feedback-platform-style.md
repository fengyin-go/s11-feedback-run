# 平台 AI 化文风与返修

2026-11-12 的 15 条平台提交中，13 条通过，2 条只因 E5「Feedback AI 化」打回；业务语义、轨迹锚点、快照、难度和时效均通过。打回原文指出：编号和时间点过密、功能被压成抽象名词、像把测试报告字段串成句，并且没有说明自己最看重什么。

## 写作防线

- 结果段用人话回答用户看到了什么，不要把功能逐项列成名词表。
- 任务编号、计划编号、时间点、处理位置、条数和工具报错只在解释问题必需时保留；一条正文通常不超过一两个。
- 过程段最多 3 句，写清卡在哪、造成什么后果、后来怎么修正。
- 自然写一句本轮最看重的业务约束，并把原句登记到 `language_review.criterion_sentence`。不要求固定使用“关键”“最重要的是”等词。
- 不直接搬 `python -I`、`_enable`、`TS7053` 等工具字段；改写成“导入不了应用”“类型检查失败”“提交动作预期写错”。
- 企业黑话、抽象包装词和机器报告式收口按 feedback-language-policy.md 处理。正文命中后先改写，不自动替换。

统一语言策略已进入新验收的语言检查回执，并绑定 `review/style-report.json`；`fbr_submit.py` 在提交/返修准备阶段仍会重新执行一次，防止导出后正文变化。旧质量回执通过语言策略版本区分，不追溯重检已交付历史。

## 2026-11-13 新规则打回

- 本批 30 条首次提交后有 9 条进入 `PENDING_FIX`：测试总数单列、计数密度和抽象摘要、问题定位不具体、2 分未明确缺口、领域规则 L2 各占一类。按下面规则返修并回读后，9 条全部转为 `QC_PASSED`。
- V2 轨迹核对会逐项比较 Feedback 里的具体日期、处理位置、状态和工具结果。没有和原始轨迹逐字一致时，不要写具体值；例如轨迹是另一个合法日期或没有明确对应关系时，写成“改成合法日期后重跑”。
- Feedback 复检不接受只报测试总数。写 `16 项测试通过` 仍无法说明覆盖范围；应逐项写清回归覆盖了唯一探测、队首、跨代理调度、中断原位、冷却等哪些需求行为。如果无法建立覆盖关系，就省略总数，只写实际验证过的行为。
- `32/32 通过`、`后端 7 项和前端 5 项通过`、`64 项服务断言通过` 同样属于只报数量。优先删除总数，直接写测试覆盖了哪些业务行为。
- 一条 Feedback 里的“两条、三次、四项、两轮”等精确计数超过约 3 至 4 个时，会读成机器摘要。只保留解释问题必需的数量。
- 过程问题不能只写“并发场景”“验证中”“过程中”出错；必须给出具体文件、模块、命令或可定位动作。
- 2 分及以下的 Feedback 必须直接写出具体问题、缺口或用户无法完成的动作，不能只描述错误现象而不收口。
- 平台领域规则 L2 打回时，先用实时 schema 核对是否存在有证据的 `sub_direction` 修订；不得为了过检随意改题面或域。

## 返修流程

```bash
# 先只读分类平台失败；不可返修项会直接转为本地废弃，不进入后续步骤
fbr_batch.py repair --batch b1110-01 --tasks s11-000123
# 仅未被本地废弃的题继续
fbr_reviewer.py review --batch b1110-01 --task s11-000123 --platform-repair --execute
fbr_reviewer.py prepare --batch b1110-01 --task s11-000123 --platform-repair --execute
# 修改 candidate 和 verification
fbr_reviewer.py finalize --batch b1110-01 --task s11-000123 \
  --candidate ... --verification ... --platform-repair --execute

fbr_batch.py repair --batch b1110-01 --tasks s11-000123
fbr_batch.py repair --batch b1110-01 --tasks s11-000123 \
  --comment "按平台打回原因重写 Feedback" --execute --confirm REPAIR
```

`repair` 只接受 `PENDING_FIX + editable=true`，保留 `locked_fields`、原轨迹和原录屏，只更新允许编辑的字段。PUT 成功后必须重新 GET：版本递增、字段一致，且 `qc_running=true` 或 `stage=QC_RUNNING/QC_WAITING`。如果请求已生效但回执未落盘，再次运行应识别 `already_applied`，不得重复 PUT。

返修后继续轮询详情：只有 `QC_PASSED` 才算通过；新的 `PENDING_FIX` 要按最新 `qc_summary` 和失败 `qc_checks` 再修。

平台返修绝对不允许修改提示词后重跑。`task.json.prompt`、`prompt.txt` 和原平台
`user_prompt` 必须完全一致；返修 reviewer/prepare/finalize 与 `repair` 都会在读写前核对。
问题若只能在改题面后通过，或属于领域、难度、工作量、A-5 查重、`DISCARDED`、不可编辑记录，
立即写 `review/platform-deprecated.json` 作为本地终态。不得换题、
重跑、重出题或继续 PUT；后续批次状态只显示“本地废弃”。

## 2026-11-14 批次返修结论

本批首次提交 38 条后，平台在首轮质检中判定了 5 条需要返修，另有 1 条因题目真实难度不足被直接作废。返修项都不是业务事实错误，而是 Feedback 的可读性和扣分解释不充分。提交前必须按下面的检查逐条排除：

- **测试层级不能代替需求验证。** “领域测试、服务层测试和生产构建全部通过”仍会被打回；应写成“服务层测试确认退役后目录与 resolver 都返回 410，并保留旧契约”。只有总数或测试层级、没有业务行为时，删掉数字并补具体行为。
- **4 分必须能看见最终交付扣分理由。** 过程句可以解释返工来源，但平台最终看的是交付缺口：
  正文末尾必须留下一个尚未闭合的验证边界、轻微功能遗漏或用户可见残留后果。只写
  “先失败、后来修正后通过、产物无问题”仍会被判为没有交付扣分点。
- **过程句避免业务速记。** “同笔落印”“只推进序号而不重刷”“封单会同笔提交”“生成覆盖带、重叠去重窗”等压缩短语会让领域外读者回读；展开为主谓完整、有因果关系的自然句子。
- **不要照搬终端成功语。** `ALL CHECKS PASSED`、`✓ built in ...` 等输出放进正文会触发 AI 化打回；改写成用户能理解的行为和结果。
- **精确程序量只保留解释问题所必需的。** 同一段连续出现撤销时长、重算天数、释放容量等多个精确值时，会像把日志和断言重排；非关键数值删除，关键值最多保留一两个。
- **4 到 5 分要有可核对落点。** 正文至少留下一个真实文件、命令、对象或实际返回值，避免只有抽象能力描述。现有 `fbr_reviewer.py finalize` 会在正文完全没有可核对线索时拦截；语义复核仍需判断该线索是否真正支持结论。
- **题目难度作废不能返修。** `DISCARDED` 和 `PENDING_FIX` 要分开处理；难度规则 P3/P4/P5
  判为题目本身不成立时不得改题重跑，直接在本地标记废弃，不改 Feedback、领域、难度字段或
  已锁定附件。

`fbr_submit.py.platform_style_problems` 现在会在上传或返修前拦截可机械识别的模式：测试层级空泛通过、精确操作量过密、终端成功输出、已知业务速记，以及 4 分缺少最终交付扣分点。当前任务 AI 仍负责判断正文里的缺口是否真实、是否与证据一致。

## 2026-11-18 自动一致性复核

平台曾一次性打回 178 条原本 `QC_PASSED` 的 4 分记录，原因均为
“交付完整性非满分（4 分），但 Feedback 未指出任何交付扣分点”。这些记录的共同写法是：
需求和产物都正常，Feedback 只写了测试失败、语法错误、断言错误或并发验证返工，最后又明确
“修正后通过、产物无问题”。旧规则把这种记录归为 `process_issue` 并给 4 分，但当前平台不认。

返修样本中可稳定通过的两种 4 分写法：

1. **真实交付问题**：主要功能可用，但最终仍有用户可观察的轻微问题。
   - 示例：需求说明文字被写进 `requirements-dev.txt`，导致依赖安装报 `Invalid requirement`。
   - 示例：全局筛选器正常，但筛选器页的导出入口仍返回 422。

2. **关键验证缺口**：主要功能可用，但题面明确的并发、时序、归档、恢复或跨模块边界尚未实跑。
   - 示例：暂停、取消和恢复只按顺序请求验证，没有让取消与恢复真正竞争。
   - 示例：重复启动与同目标竞争只按先后调用验证，没有真正同时放行请求。

这两类改写通过平台后，`score_delivery` 仍保持 4。正文必须把最终缺口放在结果段或最后一句，
不能让读者只看到过程返工。`score_basis.category` 分别用 `delivery_issue` 或
`verification_gap`，`score_basis.remaining` 必须逐字复制正文同一句。

禁止以下返修方式：

- 把纯 `process_issue` Feedback 换几个同义词后重新提交；
- 为了通过比例把全部 4 分批量改 5；
- 把未验证直接写成一定失败并批量降 3；
- 把浏览器、系统库、安装或网络问题冒充模型交付缺口；
- 修改题面、Session 或附件来绕过原记录。

`fbr_gate.py`、`fbr_quality.py` 和 `fbr_submit.py` 已增加同一门禁：4 分正文没有最终缺口，
或 `score_basis.category` 仍为 `process_issue` 时，build、lint、finalize、提交预检和返修演练都会阻断。
