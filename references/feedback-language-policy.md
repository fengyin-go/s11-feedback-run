# Feedback 语言策略

Feedback 正文只写用户能观察到的行为、结果和必要过程，不写内部黑话、抽象包装或机器报告字段。生成前按本页约束，生成后由 `fbr_style.py` 机械检查，再由当前任务 AI 完成语义复核。

## 三层规则

1. `hard_groups`：作文连接词、空泛评价、空泛完成度句。出现即拒绝。
2. `rewrite_groups`：企业黑话、比喻和无具体指向的包装词。默认出现即拒绝；必须改成具体动作、条件或结果。
3. `contextual_terms`：能力、方案、策略、机制、流程、维度等。词本身不违规，但一句里堆得过多、没有动作和结果时拒绝。

机器词表见 `feedback-style-lexicon.json`。不要在生成提示中整份复制词表，只在任务 brief 中给少量改写方向；具体命中由 lint 报告。

## 常见改写

| 不写 | 改写成 |
| --- | --- |
| 水位、水位线 | 上次处理位置、增量截止时间、下一批从哪里继续、已处理到哪条记录 |
| 链路、主链路、核心链路、调用链 | 用户从哪个入口操作、请求实际落到哪个接口、页面和后端哪里没有对上 |
| 闭环 | 操作后在哪里看到结果、失败后回到什么状态、两处数据最终是否一致 |
| 兜底 | 出错时返回什么、保留什么、显示什么提示 |
| 落地 | 已经能在页面完成、已经生效、接口实际返回了什么 |
| 对齐、拉齐 | 两处显示同一个值、使用同一份数据 |
| 打通 | 页面能调用接口、一处修改后另一处能看到 |
| 沉淀 | 保存、写入、保留 |
| 收敛 | 合并成一份、只保留一条、同一次请求只产生一个结果 |
| 编排、治理 | 按顺序执行、清理、审批、归档等具体动作 |
| 赋能、抓手、颗粒度、心智、生态 | 具体功能、入口、字段或操作 |

业务题自己使用的技术词可以保留，例如幂等、游标、事务、版本、状态机，但句子必须同时写清触发条件、实际动作和结果。`retained_terms` 要说明为什么必须保留。

## 句子结构

- 每条结果句至少落到一个动作、输入、输出或用户看到的状态。
- 不写 `X、Y、Z 均已落地/打通/对齐` 这种状态清单。
- 同一句出现三个以上抽象名词时，先拆成“谁做了什么，结果是什么”。
- 过程最多三句，优先写真实失败、修正动作和最终结果；不要写成“先实现、再验证、最后完成”的固定播报。
- 正文通常只保留一到两个定位值。任务编号、计划编号、时间、条数、退出码和错误码超过必要数量时会像测试报告。
- 同一句不要堆三个以上工具字段、错误码或精确计数。

## 语言复核

`decision-input.json` 必须填写：

```json
{
  "language_review": {
    "reviewed": true,
    "criterion_sentence": "正文中说明本轮最关键业务约束的原句",
    "translated_terms": [
      {"source": "水位", "public": "上次处理位置"}
    ],
    "retained_terms": [],
    "note": "说明术语翻译和数字取舍"
  }
}
```

`criterion_sentence` 必须逐字出现在最终正文里。`translated_terms` 可以按本题实际使用的词登记；没有时为空列表。`retained_terms` 每项写 `term` 和 `reason`，只用于确实必要的业务或技术词。

## 检查结果

`fbr_style.py` 生成 `review/style-report.json`，包含规则版本、正文 SHA、命中的原文位置、改写建议和密度指标。正文或词表变化后旧报告失效，必须重新检查。

检查器只报错，不自动改动正文。当前任务 AI 修改后仍要重新核对证据、逐句语义和评分。
